学习入口下一课：图像与 Mat独立练习
Lesson 01 / 可复现的第一步

程序到底使用了哪一份库？

目标：亲手验证依赖来源，并区分“能编译”“能运行”和“能交付”。你已掌握 Qt 开发，这一课聚焦 OpenCV 带来的新边界。

先作预测

机器同时装有 Qt 6.8.3 和 6.10.2。构建成功能否证明使用了 6.8.3？把 Release 可执行文件复制到一个空目录，它一定可以运行吗？先写下需要哪些证据。

原理：五个不同的环节

环节输入与输出典型错误
获取源码固定标签与提交 → 一份确定的源码误用开发分支或 alpha 标签
CMake 配置源码、工具链、包路径 → 构建规则找到另一份 OpenCV，或缺少组件
编译.cpp 与头文件 → 目标文件头文件找不到、类型/API 不匹配
链接目标文件与导入库 → .exe缺失实现、架构或配置不匹配
加载与运行.exe、DLL、Qt 插件 → 进程DLL 找不到、平台插件缺失

链接时使用的 .lib 不能替代运行时 .dll。编译时的 CV_VERSION 来自头文件；演示同时打印 cv::getVersionString() 来检查运行库。精确版本查找、编译器校验、双配置测试和干净环境部署共同构成证据。

Debug 与 Release

两者使用同一算法，但优化、调试信息、断言和运行库配置不同。这里 Debug 使用 /MDd、Release 使用 /MD，OpenCV 与应用分别构建。不要把同名头文件当成二进制可混用的保证，也不要拿 Debug 耗时评价最终性能。

实验一：准备并解释环境

首次按项目 README 生成本机预设，再从仓库根目录运行。脚本只修改自己的进程环境，不修改全局 PATH。

./scripts/PrepareDependencies.ps1
./scripts/Build.ps1 -Configuration Debug
./scripts/Build.ps1 -Configuration Release
./scripts/Run.ps1 -Configuration Debug -Program environment_probe

检查输出中的 Qt 6.8.3、OpenCV 头文件和运行库 5.0.0、C++20、x64、MSVC 及配置名称。基础矩阵加法的检查值应为 3；若不是，先定位构建或数据问题，不继续后续课程。

你应该观察的中间结果

  • build/deps/install/Debug 和 Release 分开，里面的构建记录包含提交与选项。
  • CMake 配置日志显示找到的 Qt/OpenCV；应用诊断输出提供运行时证据。
  • 测试输出包含通过/失败数量，不能只看进程“没有崩溃”。
  • 可执行文件旁出现时间命名的日志，Debug 可见函数进入和退出。

实验二：验证部署

./scripts/Deploy.ps1

部署脚本复制所需 OpenCV DLL，并用匹配的 windeployqt 准备 Qt 依赖，最后用去掉开发目录的 PATH 启动部署副本进行烟雾测试。该结果证明当前机器的干净进程环境可运行；仍不等同于在另一台未装运行库的机器完整验收。

失败案例与排查顺序

现象先检查不要这样“修”
CMake 找不到 OpenCV依赖脚本是否成功，配置是否一致随便从其他版本复制 DLL
启动缺 DLL部署目录内容与运行时搜索路径把开发目录永久加入全局 PATH
Qt platform plugin 错误platforms/qwindows.dll 与匹配的 Qt 依赖混放不同 Qt 安装中的插件
版本校验失败本机预设与所选工具链删除精确版本约束绕过检查

自测：先回答，再展开

为什么只打印 CV_VERSION 还不够？

它反映编译时头文件版本。需要同时确认链接和运行库来源；演示增加运行时版本输出，部署测试进一步验证实际可加载依赖。

为什么两个配置不安装到同一个混合目录？

分开能清楚记录每份构建的运行库、组件与 DLL 来源，降低链接或部署误选配置的风险，也便于独立重建。

Qt 负责界面，是否必须让 OpenCV 自己启用 Qt 后端？

本项目通过 Mat 到 QImage 转换显示，不依赖 OpenCV HighGUI，因此无需 WITH_QT。两套库在应用中连接即可。

独立练习与验收

完成练习目录中的环境报告。必须附自己的诊断输出，分别说明一个配置、链接和运行时错误。不要故意破坏原安装；故障实验只在临时部署副本进行。

复盘时应能回答：“这次构建用了哪份头文件？哪份 DLL？凭什么知道？”下一课开始前再凭记忆回答一次。
